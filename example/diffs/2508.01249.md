# Diff: arXiv 2508.01249 — "Securing Large Language Model Agents via Structured Graph Abstraction" (AGENTARMOR, ByteDance, v3 18 Nov 2025)

## Skip

- **Graph abstraction of security-relevant agent execution as the core move** (p.2, p.4 §5): AgentArmor abstracts the runtime trace into a Program Dependence Graph whose nodes are executed actions/decisions and whose edges are dependencies. The notes' line on the Skill Impact Graph — "nodes represent security-relevant states and skill invocations induce transitions between them" — already carries the idea that the defense is formulated over a graph of agent execution. What differs is the node semantics (see Read), not the premise.
- **Untrusted-input-to-dangerous-action threat framing** (p.3 §3, p.3–4 §4 case studies A/B/C): external attacker injects via content the agent is instructed to process, aiming to induce unsafe tool calls; model-level attacks and compromised tool binaries are out of scope (p.3). This is the same indirect-prompt-injection setting the notes' title line assumes, so §3 and §4 need no reading beyond the case studies.
- **Parameter-level rather than tool-level control** (p.1, p.5 §5.1(3), p.13 §7): the argument that prior system-level defenses "treat an action as a whole object, lacking fine-grained data dependency analysis on action parameters" (p.13) is the same motivation as the notes' steerability-signature line, which likewise refuses to control at tool granularity and instead constrains each skill parameter.
- **Inline pre-execution mediation** (p.8 §5.3 step 3, "the inspector blocks the action node"): matches the notes' inline reference monitor mediating invocations. Mechanism of the check differs (see Read); the placement does not.
- **Distrust of natural-language semantics as a safety signal** (p.3–4 §4, p.13 §8 "LLM-based dependency reasoning"): AgentArmor's stated limitation is that its dependency inference "relies on another LLM, leaving space for attacks to bypass" (p.13). The notes already record this conclusion — "Determining whether such influence is safe from the natural-language semantics of argument is unreliable" — and take the opposite design branch.

## Read

- **§5.1(5) Dependency analyzer and Table 1, p.6–7.** New: eight named reasoning patterns (Direct User Request, Indirect Execution, Parameterized Execution, Functional Execution, Conditional Execution, Transfer Execution, Multiple Source Execution, Unauthorized Indirect Execution), each with a formal representation and the control/data dependency it implies. This is the paper's taxonomy of *how* a tool call's provenance can be structured — the input side of what the notes call the steerability signature, and a vocabulary the notes have no equivalent for.
- **§5.2 Type definition, p.7–8.** New: `Type := {security type, rule type}`, with security type split into confidentiality and integrity, each in {low, mid, high} on a lattice. The notes' capability model is a set (initial capability set plus forbidden state B); this is a lattice-valued annotation per node instead, which is a different formal object with different closure properties.
- **§5.2 Type infer, p.8.** New: type propagation rules — single-source propagation inherits the source's type; multi-source join takes the most restrictive confidentiality and the *least* restrictive integrity. This is the paper's answer to nodes that cannot be predefined; the notes' mechanism recomputes restrictions on contamination instead of propagating labels.
- **§5.1 property registry (tool registry + data registry), p.6, p.8.** New: trusted metadata supplies intra-tool data flow and side-effect nodes that the runtime trace does not expose (the `search_email` → `email_data` side-effect node, p.6), and supplies initial type assignments (p.8). This is the paper's trusted-input assumption, the counterpart of the notes' "given sound skill summaries and policies."
- **§5.3 Graph inspector, p.8.** New: three-step enforcement — rule extraction, constraint evaluation against the lattice, violation resolution by blocking. Crucially the enforcement action is *block this node*, with no notion of minimum-cut or of reducing a capability set. Read this against the notes' capability restriction mechanism: it is the same job done without a reachability computation.
- **§6.5 Failure case analysis and Fig. 11, p.12.** New: the residual failure mode is "transfer execution" — the user prompt legitimately delegates control to an observation ("read the file and follow the instructions precisely"), so the injected instruction inherits authorization. The paper reports it cannot resolve this at the system level and ships two settings, allow and disallow. Most directly relevant section for the notes: it is the case where provenance is correct and the policy is still wrong.
- **§6.6 System overhead, p.12.** New: cost breakdown by component and a wall-clock comparison against seven baselines. Nothing in the notes addresses cost.
- **§7 Access control, p.13.** New: the paper's own positioning against data-labeling IFC systems and against declarative policy/DSL approaches, with the specific criticism that DSL approaches "can not track the sensitive data flow among the agent runtime."
- **§8 Limitations, p.13.** New: three limitations beyond the LLM-dependence one — no "end" action so DoS is out of reach; rule types are predefined and not generated per task; transfer execution unmitigated.

## Disagreements

Between the paper and the notes:

- **Enforcement primitive.** Notes: "SkillGuard recomputes capability restrictions upon state contamination, disconnecting all paths to forbidden states on the execution graph at a minimal cost… evaluates the reachability from the current state q to the forbidden set B." Paper, p.8 §5.3: "When a violation occurs, the inspector blocks the action node." AgentArmor's graph is analyzed by local type-check on nodes and edges ("the inspector traverses the PDG and checks that all data and control dependencies satisfy the confidentiality and integrity lattice", p.8), not by a reachability query to a forbidden set and not by a minimum cut. The two papers put a graph at the centre and then do different things with it; the notes' minimality-of-cost criterion has no counterpart here.
- **What the graph's nodes are.** Notes: "nodes represent security-relevant states." Paper, p.3 §2.2: "each node corresponds to an executed action or decision," elaborated p.5 into tool-name, tool-parameter, tool, observation, LLM and thought nodes. A state-transition graph and a dependence graph over trace elements are not interchangeable; a page-4-to-8 reading should treat the correspondence as loose.
- **Whether a system-level defense can cover delegated control.** Notes treat forbidden-state reachability as disconnectable in general. Paper, p.12 §6.5: "since AGENTARMOR provides the defense at the system level, such transfer execution is hard to deal with," and p.13 §8: "Current AGENTARMOR lacks the ability to mitigate the uncovered attacks." The paper's proposed fix is task alignment — "understand whether current instructions align with the original user prompt" (p.13) — i.e. a return to semantic judgement, which the notes' steerability-signature line rejects as unreliable.

In-paper inconsistencies, recorded not resolved:

- **ASB TPR.** p.11 §6.3 prose: "This is due to the 0.01 TPR and a near-zero FPR (0.02 and 0.00)." Table 2, p.10: every ASB row reports TPR 1.00. The prose figure is also self-defeating as written (a 0.01 TPR would not explain a 0.00 ASR).
- **Transformers PI detector on banking.** p.10 §6.2 prose: "transformer pi detector outperforms AGENTARMOR in banking (Fig. 6(a)) and travel (Fig. 6(c))." The Fig. 6(a) number run on p.9 places the detector at 0.11 against AgentArmor at 0.05, i.e. the opposite ordering for banking; Fig. 6(c) at 0.09 against 0.06 likewise. Figure 6 is among the garbled bar charts, so the label-to-value mapping is inferred — flagging the conflict rather than asserting which side is wrong.
- **Constructor share of time cost.** p.12 prose: "the graph constructor dominates, accounting for 69.6% of the total time." The Fig. 12(a) label text on p.12 reads 69.3%.
- **SecAlign comparison direction.** p.11 §6.2: "SecAlign shows overall better performance from AGENTARMOR, but the improvement is rather small" — then the section is titled a comparison in which AgentArmor's selling point is that SecAlign requires fine-tuning. The sentence as printed is ambiguous about which system is better; the accompanying numbers (ASR 1% lower, utility 4% higher for SecAlign) favour SecAlign on both axes.
- **Headline ASR vs per-model spread.** Abstract and §9 state 3% ASR (p.1, p.13). §6.3 reports 4% for GPT-4o (p.11) and §6.4 reports 5.2% for GPT-4o (p.11–12) — two different numbers for the same model-benchmark pair, with the abstract's 3% being the GPT-4o-mini default only.
- **Units in §6.4.** p.11–12 gives Claude ASR as "0.03%" and utility as "87.0%", while Fig. 9 and Table 2 report ASR as a fraction; 0.03% is three orders of magnitude from the 0.03 that the rest of the paper uses.
- **§5.1 step numbering vs Fig. 2.** p.5 narrates node decomposition, control flow edges, control dependency, node filtering, data flow edges, data dependency, registry integration and PDG assembly against Fig. 2's markers 1–8, but the marker digits in the extracted caption and body do not line up consistently; treat Fig. 2's step order as the authority once a clean copy is available.

## Reading order

Given the notes, read in this order:

1. **§5.1(5) plus Table 1, pp.6–7.** The eight reasoning patterns are the single most transferable artifact for the notes' steerability-signature work: a provenance taxonomy the notes currently lack.
2. **§6.5 and Fig. 11, p.12.** Transfer execution is the failure mode that a reachability-and-cut formulation has to answer for too, since the path to the forbidden state is authorized by the user's own prompt. Read before committing to the notes' claim that unsafe paths can be disconnected.
3. **§5.2 and §5.3, pp.7–8.** The lattice-plus-rule-type alternative to a capability set, and what enforcement looks like without reachability. Read as the contrast case for the notes' capability restriction mechanism.
4. **§6.6 and Fig. 13, p.12.** Cost of doing graph analysis per tool call, with the constructor identified as the expensive part — the budget the notes' approach will be compared against.
5. **§6.2, pp.10–11.** The Progent and Camel numbers, since those are the system-level defenses the notes' work will also be measured against.
6. **§7 Access control, p.13.** The paper's framing of data-labeling IFC versus policy-DSL, useful for placing SkillGuard among both.
7. **§4 case studies A–C, pp.3–4.** Skim only; three concrete injection chains, useful as examples but conceptually already in the notes.
8. **Appendix Table 3 and Fig. 14** — unavailable in this extraction (pp.15–17 empty). Fetch the PDF directly if the node-type list or the worked construction example is needed.
