## Skip

## Read

- **p.6–7 §4.1 "Agent Isolation" (trusted agent A_T / untrusted agent A_U, privileged token T_P / unprivileged token T_U)** — new: confinement is achieved by *splitting the agent into two principals with separate OAuth-style access tokens*, not by editing a graph. The notes' mechanism restricts capability within one agent; PFI's restriction is a static two-domain partition fixed before execution.
- **p.7 §4.2 "Data ID" and p.7–8 "Data Referencing" / "Computation Offloading"** — new: untrusted tool results are replaced by opaque identifiers (`#DATA0`, `#DATA1`) held in a data-ID table, so the trusted agent can *pass* untrusted values into tool arguments without ever seeing them. The notes have no data-masking primitive; steerability signatures constrain a parameter's type and range, whereas data IDs constrain the trusted agent's *visibility* of the value.
- **p.8 "Prompt Transformation"** — new: an explicit, gated promotion of untrusted data to active prompt, allowed only when (i) the trusted agent requests `prompt` type and (ii) the user approves. This is the closest analogue in PFI to the notes' contamination event, but it is resolved by a human prompt rather than by recomputing a cut.
- **p.8 §4.3 "Data Flow Guardrail" (DataGuard) and "Control Flow Guardrail" (CtrlGuard)** — new: mediation triggers are *deterministic syntactic indicators* — presence of a data ID in a tool argument or final answer, and presence of a `prompt`-typed query response — rather than reachability from the current state to a forbidden set. Explicitly contrasted on p.8 with guardrails that "rely on LLMs or ad hoc rules."
- **p.8–9 "Security Attributes" (Attr)** — new: provenance metadata (source tool, web origin, file owner, sharing level) travels with each data ID and is *conservatively aggregated* over the whole untrusted context when A_U returns a response. A taint-style over-approximation; the notes carry no provenance-propagation rule.
- **p.9 "Guardrail Alert"** — new: the alert surface is specified as source raw value + Attr, sink (tool argument or location in final answer), and flow type. The notes' monitor blocks; PFI's monitor asks.
- **p.10 §4.4 "Access Token Privilege"** — new: default is T_P full / T_U none, with tool developers declaring per-tool sensitivity by analogy to Google API scopes. Relevant to how the notes' "initial capability set" would be populated in practice.
- **p.10–11 §5.1 benchmark extension** — new: AgentDojo and AgentBench OS were *modified* to carry data-injection (not just prompt-injection) attacks, and tools were rewritten to honour access tokens; the shell tool was sandboxed with nsjail. Relevant if the notes' work is to be evaluated on the same beds.
- **p.11 §5.1 "Evaluation Metrics" — Secure Utility Rate (SUR) and Attacked Task Rate (ATR)** — new metric definitions: SUR = task success AND attack failure; ATR = fraction of user tasks attacked regardless of completion. Note the definitional choice: "If an agent alerts and warns the user about potential security risks, we considered the attack unsuccessful."
- **p.12 "Failed Utility Tasks"** — new: a failure taxonomy for why the confinement mechanism itself costs utility (models mishandle the indirection).
- **p.13 "Accuracy of Guardrail Alerts"** — new: a *design argument* (not a measurement) that false positives and false negatives are both impossible, plus a log audit for the false-negative side.
- **p.13 "Cost Evaluation"** — new: the overhead of running a second agent, quantified.
- **p.14 §6 "Discussion"** — new: the authors' own stated weak points — utility loss, policy authorship, and reliance on manual user inspection.
- **p.17–19 Appendix A (Tables 4 and 5)** — new: a fully worked per-tool privilege assignment over 75 benchmark tools and the concrete trusted-Attr list. Usable as a ready-made policy corpus.
- **p.21 Appendix C (Figures 9 and 10)** — new: the verbatim system prompts for A_T and A_U, including the query type vocabulary (`bool, int, float, email, url, phone, date, datetime, time, prompt, string`). Closest concrete artefact to the notes' steerability signatures.

## Disagreements

1. **Where the security decision is made — monitor vs user.**
   Notes: "SkillGuard recomputes capability restrictions upon state contamination, disconnecting all paths to forbidden states on the execution graph at a minimal cost."
   Paper: "If a guardrail detects an unsafe flow, it raises an alert to the user, asking for approval to proceed with the operation." (p.8) and "PFI requires user approval before allowing the prompt transformation." (p.8)
   The notes describe an automatic, cost-minimising recomputation with no human in the loop; PFI's response to the same trigger is to suspend and ask. PFI itself names this as a limitation: "users might lack the expertise to make informed decisions or blindly approve them for convenience" (p.14).

2. **What counts as a prevented attack.**
   Paper: "If an agent alerts and warns the user about potential security risks, we considered the attack unsuccessful since the user may decide not to proceed." (p.11)
   Under this rule the 0.00% ATR in Table 1 (p.12) and the "deterministic security guarantee" claim (p.12) credit PFI for every alert raised, whether or not a user would actually deny it. The notes' mechanism disconnects the path itself, so the two 0% figures are not the same quantity and should not be compared directly.

3. **Basis for constraining influence over arguments.**
   Notes: "Determining whether such influence is safe from the natural-language semantics of argument is unreliable. Instead, SkillGuard defines explicit constraints for each skill parameter … the type and permitted value range of each parameter."
   Paper: PFI's type system (p.21, Figure 9) covers types only — `bool, int, float, email, url, phone, date, datetime, time, prompt, string` — with no value-range constraint; safety comes from the argument's *provenance* (is it a data ID?) rather than from any admissible-value predicate. The two papers agree that NL semantics is the wrong basis and diverge on the replacement.

4. **In-paper inconsistency: headline SUR figures.**
   p.2: "increasing from 27.84% to 55.67% on AgentDojo and from 2.63% to 67.79% on AgentBench OS, across diverse models."
   p.12: "PFI achieved the highest SUR among LLM agents, with 61.86% on AgentDojo and 68.42% on AgentBench OS … Baseline, which had an SUR of 12.37% on AgentDojo and a zero SUR on AgentBench OS."
   Neither the baseline nor the PFI number matches between abstract and results section. The four-model means from Table 6 (p.20) are AgentDojo Baseline 27.835 / PFI 55.67 and AgentBench OS Baseline 2.63 / PFI 65.79 — so the abstract appears to be the cross-model mean and p.12 the GPT-4o row, but the AgentBench OS PFI figure (67.79% on p.2 vs a 65.79% mean from Table 6) does not reconcile under that reading. Recorded, not resolved.

5. **In-paper inconsistency: size of the utility-failure sample.**
   p.12: "For each LLM model, we analyzed 108 tasks that where successfully completed by Baseline but failed in PFI."
   p.19 §B.1: the evaluated suites contain 97 AgentDojo utility tasks and 19 AgentBench OS utility tasks, 116 in total. A per-model Baseline-success-but-PFI-failure set of 108 out of 116 is not consistent with the SUR/STR figures in Table 6 (p.20) — e.g. GPT-4o Baseline STR 81.44% vs PFI 61.86% on AgentDojo implies a gap far smaller than 108 tasks. Recorded, not resolved.

6. **In-paper inconsistency: f-secure figure described as an average.**
   p.12: "f-secure achieved an average SUR of 40.21% on AgentDojo and 10.53% on AgentBench OS," but the comparison is introduced against Figure 7a, which is captioned as GPT-4o only (p.12). The word "average" has no stated basis. Recorded, not resolved.

## Reading order

Given the notes, read in this order:

1. **p.8 §4.3, "Data Flow Guardrail" through "Guardrail Alert" (through p.9)** — the inline-mediation layer, and the direct counterpart to the notes' reference monitor. Read first because it is where PFI and SkillGuard make the same decision differently.
2. **p.7–8 §4.2, "Data ID" through "Prompt Transformation"** — the data-ID indirection, which is the mechanism the guardrails are built on and the one idea in PFI with no analogue in the notes.
3. **p.21 Appendix C, Figures 9 and 10** — the concrete type vocabulary and prompt contract; read directly against the steerability-signature bullet.
4. **p.6–7 §4.1 and p.10 §4.4 "Access Token Privilege"** — how the capability set is actually populated and split; read against the "initial capability set" bullet.
5. **p.11 §5.1 "Evaluation Metrics" and p.12 Table 1** — SUR/ATR definitions before any number is reused, because of Disagreement 2.
6. **p.13 "Cost Evaluation"** — the price of a two-agent design, a cost the notes' single-graph approach may avoid.
7. **p.17–19 Appendix A, Tables 4 and 5** — reusable per-tool privilege and trust policy for the 75 benchmark tools.
8. **p.5 §3.3 "Previous Defenses"** — IsolateGPT, f-secure LLM, AirGap positioning; read last, as orientation rather than content.

Skip §1–§3.2 (p.1–5) except §3.3, and skip §6 Discussion (p.14) unless the utility-cost question is live.
