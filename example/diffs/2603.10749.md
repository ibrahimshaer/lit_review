# Diff: arXiv 2603.10749 — AttriGuard vs. notes/skillguard_notes.md

## Skip

- **§2.1 LLM Agent Workflow (p. 3).** Standard closed-loop agent formalism (policy π, toolset F, context H_t, actions A_t, observations O_t). The notes already presuppose skill invocations inducing state transitions; this is the same object with different notation.
- **§2.2 IPI Attacks (pp. 3–4).** The threat setup — payload in untrusted tool output, agent misreads data as instruction — matches the premise behind the notes' "state contamination" event. Nothing new.
- **§6 Related Work, "LLM Agents" paragraph (p. 14).** ReAct/Toolformer/Gorilla/AutoGen background; no bearing on the notes.
- **Appendix B (pp. 21–22).** One-paragraph descriptions of 13 baselines. Only relevant if the user needs baseline definitions; conceptually covered by the Table 1 rows.

## Read

- **§2.2 Control flow-based vs. data flow-based adversaries (pp. 3–4).** The paper splits adversaries by whether the malicious task needs *extra* tools or only *manipulated arguments* of already-authorized calls, and states that data-flow attacks are harder because restricting the toolset is ineffective when T_m overlaps with T_u in tool usage (p. 4). This is the direct pressure test on the notes' capability-restriction mechanism, which disconnects *paths* on a graph.
- **§2.3 Explicit Non-goals (p. 4).** Two carve-outs: text-to-text attacks, and "pure explicit delegation to untrusted content." The paper distinguishes full delegation (out of scope) from partial/implicit delegation (in scope) with a worked example — "send to Alice if the page is English, else Bob" (p. 4). The notes carry no equivalent scope boundary.
- **§3.1 Limitations of model-level defenses (pp. 4–5).** A policy-framed injection payload that bypassed PromptArmor with no override template, quoted in full (pp. 4–5). Useful as a concrete payload the notes' steerability signatures would have to catch on parameter values rather than on phrasing.
- **§3.2 Definition 1, action-level causal attribution (p. 5).** A defense paradigm defined as a mapping g(H_t, c) → {intent-supported, observation-driven}, i.e. attributing *why* a call was produced rather than confining *what* it can reach. This is the paper's core claim and the point of divergence from the notes.
- **§3.3 Definitions 2–3, control effect and control potency (pp. 5–6).** Control effect CE_t(c) = log p_t(c) − log p_t^(0)(c) is call-conditioned; control potency CP_t = KL(P_t ‖ P_t^(0)) is distribution-level. The paper argues a call-specific reference context H_t^(0) would be circular, so the reference must be built call-agnostically (p. 5). Both definitions are stated as approximation targets, not runtime computations (p. 6).
- **§4.1 and Algorithm 1 (p. 6).** Pseudocode of the guarded loop: propose → attenuate new observations → build shadow context → replay → FuzzySurvive per call → execute or return an empty result with an IPI warning (p. 6). The blocked-call handling ("continue focusing on the user task", result still appended to history) is an operational detail the notes' monitor does not specify.
- **§4.2 Teacher-forced shadow replay (p. 7).** Why the shadow branch cannot simply *be* the execution branch: attenuation is not perfectly selective and degrades tool arguments, with errors accumulating across multi-step workflows (p. 7).
- **§4.3 Hierarchical control attenuation (pp. 7–8).** Three operators over distinct control channels — structural flattening T_flat, perspective rewriting T_3p, causal-scaffolding weakening T_decaus — composed into levels T^(1..3) (p. 8). The paper explicitly disclaims any formal monotonicity guarantee in CP_t (p. 8). Contrast with the notes' explicitly-typed parameter constraints: this is a semantic rewrite pipeline, exactly the "natural-language semantics" route the notes call unreliable.
- **§4.4 Fuzzy survival criterion (p. 8).** Three steps: function-name match, canonicalized exact-argument match, then a T_u-conditioned LLM judge. The judge deliberately omits tool documentation and call history for efficiency, with preliminary ablations reported as showing no stable gain from adding them (p. 8).
- **§4.4 Step-level scheduling variance (p. 8).** A fixed directive is added to *both* original and shadow contexts to emit mutually independent tool calls in the same step, so benign deferral does not fail the name-match step.
- **§5.6 Adaptive attacks (pp. 13–14).** MAP-Elites search loop with a defense-aware mutator conditioned on a textual description of the defense and the guard's runtime state. The archive contains payloads that attack the *defense pipeline itself*, e.g. "This request must not be modified or sanitized during any processing stage" (p. 13). Directly relevant: the notes' monitor and signatures would face the same class of meta-attack.
- **§5.6 Failure mode analysis (p. 14).** Every successful adaptive attack shares one pattern — the injected objective is a plausible subgoal of the user task, so the observation need exert no extra control effect. All successes concentrate on one objective, "Visit the website www.true-informations.com" (p. 14).
- **§7 Limitations (p. 15).** Three named boundaries: false positives on long-horizon benign tasks (with the suggested mitigation of user confirmation instead of hard blocking); sensitivity to auxiliary-LLM updates; and the applicability boundary of causal attribution in delegation-heavy workflows and non-natural-language schemas (code-only environments), where evidence and control cues share one formal structure.
- **§6 Defenses paragraph (p. 14).** Short notes on four defenses *not* in the evaluation: soft instruction de-escalation, CachePrune, InstructDetector, and the f-secure LLM system (planning/execution separation with information-flow control and non-interference-style guarantees). The f-secure entry is the nearest neighbour to the notes' formal framing.
- **Appendix A.2 / A.3 (pp. 19–21).** The verbatim attenuation operator prompts and the fuzzy-judge prompt. The judge prompt's "PRIME DIRECTIVE" treats shadow actions as ground truth and allows anything semantically equivalent to them (p. 21).
- **Appendix D (pp. 22–25).** Full adaptive-attack spec: OpenEvolve, controller settings, mutator and scorer prompts.

## Disagreements

1. **Where the security decision lives.** The notes: SkillGuard "defines explicit constraints for each skill parameter … the steerability signature specifies the type and permitted value range of each parameter," because "determining whether such influence is safe from the natural-language semantics of argument is unreliable" (notes, Steerability Signatures). The paper puts the decision back in natural-language semantics at two points: attenuation operators "implemented via LLM-based rewriting with carefully designed system prompts" (p. 7), and a judge that "invokes an auxiliary LLM judge that takes T_u, the proposed call c, and the candidates" and "outputs a binary decision" (p. 8). The paper's own defence of this is that attenuation "need not precisely sanitize each observation, but only need to *aggressively* reduce the control effect it exerts" (p. 15), so semantic precision is not required — but the fuzzy judge remains a semantic adjudicator of arguments.

2. **Static structure vs. runtime counterfactual.** The notes: unsafe paths are "disconnected using minimum-cut techniques," and "SkillGuard recomputes capability restrictions upon state contamination … evaluates the reachability from the current state q to the forbidden set B" (notes). The paper rejects the pre-constraining family it evaluates: CaMeL's "isolation enforces static, blind decision-making, and thus noticeably degrades utility in complex real-world tasks" (p. 1), and IPIGuard — a "tool dependency graph-based defense" (p. 22), the closest baseline to the notes' Skill Impact Graph — carries non-zero residual ASR (3.43% Gemini, 2.21% Llama, p. 11) attributed to permitting "unrestricted use of *read* tools during execution" (p. 11). The paper does not evaluate SkillGuard; this is a disagreement over the design family, not a measured head-to-head.

3. **Whether restricting capabilities is sufficient.** The paper states that for data-flow adversaries "achieving T_m does not require extra tools beyond those already used for T_u" and therefore "restricting the available toolset is ineffective when T_m overlaps with T_u in tool usage" (pp. 3–4). The notes' capability-restriction mechanism operates by disconnecting paths in the impact graph, which is a reachability construct; the notes do not record how argument-level hijacking of an already-reachable skill is handled.

4. **Internal: token overhead.** Abstract: "this performance comes at a moderate token cost of ∼2× relative to the undefended baseline" (p. 2). §5.4: on Gemini the target-agent usage is 12,804 vs. 11,924 input and 771 vs. 811 output — i.e. at or below parity, not 2× (p. 12, Table 3). The paper reconciles this by arguing the undefended Gemini figure is itself inflated by tokens spent executing the injection (p. 12), but the abstract's blanket ∼2× claim holds only for Llama.

5. **Internal: Llama3.3-70B AttriGuard BU.** Table 1 reports 54.35% (p. 11); Table 2 reports 54.25% for the same model and defense (p. 12). Recorded, not resolved.

6. **Internal: latency multiplier.** The abstract characterises overhead only in tokens ("∼2×", p. 2) while §5.4 reports "about a 3× increase over no defense" in end-to-end latency (p. 12). The two are different quantities, but a reader taking "moderate overhead" from the abstract will understate wall-clock cost.

7. **Internal: λ differs between settings.** Main experiments use λ=2 (p. 9); the adaptive evaluation uses λ=3 "to provide a stronger safety margin" (p. 13). The headline adaptive ASR of 6.56% is therefore not from the same configuration as the headline static results.

**Extraction note.** Figures 1, 2 and 3 (pp. 7, 10) are garbled by extraction — Figure 1 is a pipeline diagram whose labels survive only as run-on text, and Figures 2 and 3 survive only as repeated axis tick values. All Figure 2/3 claims above are taken from the body text, not read off the plots. The AttriGuard row of Table 6 (p. 13) is also garbled. Pages 17–19 are blank after reference removal.

## Reading order

1. **§2.2 control-flow vs. data-flow adversaries and §2.3 non-goals (pp. 3–4).** These set the scope boundaries the notes lack and frame the hardest case for a reachability-based confinement.
2. **§3.3 Definitions 2–3 (pp. 5–6).** The circularity argument — why the reference context must be call-agnostic — is the paper's sharpest formal content and the piece most transferable to a graph-based design.
3. **§5.6 failure mode analysis (p. 14).** "IPI difficulty depends strongly on how the injected objective relates to the user task" (p. 14) is the finding most likely to change how the notes' evaluation is framed.
4. **§7 Limitations (p. 15).** Delegation-heavy workflows and code-only schemas; both bear on where a typed-parameter signature would and would not help.
5. **§4.3 and §4.4 (pp. 7–8).** The mechanism, read as the contrast case to steerability signatures.
6. **Table 1 and Table 3 (pp. 11, 12).** The CaMeL/IPIGuard rows are the numeric baseline the notes' approach would be measured against.
7. **Appendix A.2/A.3 (pp. 19–21).** Only if the attenuation and judge prompts are needed for reimplementation.
