## Read

- **§3.2, Permission hierarchy reconstructed from OAuth scopes (p. 5).** New: the security-relevant structure is derived mechanically from each service's *published OAuth configuration* — scope `s1` is a child of `s2` iff its supported method set `O1 ⊆ O2` — rather than from per-skill summaries or hand-written policies. The notes' Skill Impact Graph has no equivalent automatic-derivation story.
- **§3.2, naming-vs-function finding (p. 5).** New: scope names systematically misstate the real hierarchy (`*.events.readonly` is *not* the parent of `*.events.owned.readonly`); repeated for Outlook's `Mail.Read` / `Mail.ReadWrite` (p. 10).
- **§3.3, ILP formulation of least privilege (pp. 5–6).** New: minimal permission selection is an integer linear program over binary node variables `x_v`, minimizing `Σ cost(v)·x_v` subject to `Σ_{v: subtree(v)∩S_i ≠ ∅} x_v ≥ 1` per API call. This is the structural counterpart to the notes' min-cut: both are optimization-over-a-graph, but the objective is *minimum-cost covering of required capability*, not *minimum-cost disconnection from a forbidden set*.
- **§3.3, incremental re-solving (p. 6).** New: previously granted scopes are pinned to 1 and the ILP is re-run for the delta. The notes describe recomputation on contamination but not monotone accumulation of prior grants.
- **§4.3, session-based mobile permission model (p. 7).** New: four grant options — Always allow / Allow once / Allow this session / Don't allow — with per-session forks of the permission set discarded at session end. Nothing in the notes involves a human authority.
- **§4.4 and Fig. 5, in-scope vs out-of-scope attacks (pp. 7–8).** New: explicit statement that a plan altered *within* already-granted permissions is not defended, including "the same tool call with different arguments" (p. 8).
- **§5, synthetic dataset over 10 real applications (pp. 8–9).** New: an evaluation substrate built from real OAuth configurations (Gmail, Google Calendar, Google Drive, Google Storage, Slack, Dropbox, Outlook, Outlook Calendar, Notion, Zoom), with single-method / multi-method / multi-application scenarios.
- **§5.1, hierarchy shape varies by provider (p. 9).** New: deep trees (Google family) versus flat forests of height ~1 (Slack, Zoom, Dropbox), attributed to differing provider design philosophies.
- **§6.2.1, audit of shipped connectors (p. 11).** New: the solver is turned on real ChatGPT and Claude connectors and finds six overprivileged configurations.
- **§7.2, fine-grained access control as future work (pp. 12–13).** New: argument-level constraint (e.g. restricting a Slack send to the specific recipient in the plan) is named as an *extension point that MiniScope deliberately does not implement*, citing permission-fatigue risk. This is precisely the design point the notes' steerability signatures occupy.
- **§8, related-work taxonomy (p. 13).** New: names and one-line characterizations of f-secure, IsolateGPT, ACE, AirGapAgent, CaMeL, PFI, and the Dual LLM pattern.

## Disagreements

1. **Argument-level control.** The notes: "Determining whether such influence is safe from the natural-language semantics of argument is unreliable. Instead, SkillGuard defines explicit constraints for each skill parameter… the steerability signature specifies the type and permitted value range of each parameter" (notes line 7). MiniScope: "MiniScope does not provide guarantees against attacks that alter the execution plan within the currently granted permissions. For example, such attacks may mislead the agent into invoking another tool call within the same permission group or the same tool call with different arguments" (p. 8, §4.4), and argument analysis is listed only as future work — "By examining the arguments passed to each tool call, we can determine not just which methods are needed, but which specific resources will be accessed" (p. 13, §7.2). The two papers place the same problem on opposite sides of the system boundary.

2. **Where the defense's authority comes from.** The notes describe a fully mechanical pipeline: given summaries and policies, the monitor recomputes restrictions on contamination and cuts paths to `B` (notes lines 3, 9) — no human. MiniScope: "MiniScope treats the user as the ground-truth authority and prompts for explicit approval" (p. 2, §1), and "we treat users as the ground truth source for permission decisions" (p. 7, §4.3). MiniScope's own limitations section concedes the cost: "users may still make mistakes, either by approving overly broad requests or by overlooking subtle risks" (p. 13, §7.3).

3. **What the graph is.** The notes: "nodes represent security-relevant states and skill invocations induce transitions between them," with safety enforced by disconnecting paths to a forbidden set `B` via minimum cut (notes lines 5, 9). MiniScope: nodes are *permission scopes* and an edge `(v_i, v_j)` means "`v_i` grants broader permissions than `v_j`" (p. 6, §3.3) — a static sensitivity lattice, not an execution-state transition system, and the optimization is a minimum-cost cover, not a cut. Both call the object a graph and both optimize over it; they are not the same formalism.

4. **In-paper inconsistency — latency overhead.** Abstract: "MiniScope incurs only 1–6% latency overhead" (p. 1); §6.3: "incur only 1–6% runtime overhead" (p. 11); §1: "MiniScope adds only 1–7% runtime overhead" (p. 3). Recorded, not resolved.

5. **In-paper inconsistency — Claude's overprivileged service.** The text states "its Google Drive integration includes an optional scope that enables file modification and deletion beyond its stated read only behavior" (p. 11, §6.2.1), but Tab. 3 (p. 11) has no Google Drive row; its rows are Gmail, Google Calendar, Google Storage, Notion, Dropbox, and the only Claude row with a gap is Google Storage (45 → 27). Recorded, not resolved.

6. **In-paper inconsistency — LLMScope quality reported two ways.** §1 states the LLM baseline "reaches only 70–83% optimality with proprietary models, and drops to 20–34% with open source models" (p. 3), but §6.2 reports the same experiment exclusively as per-application mismatch rates split into overprivileged and infeasible (p. 10), and Tab. 2 as overprivilege ratios (p. 11). No aggregate optimality figure appears in §6 to check the §1 claim against. Recorded, not resolved.

7. **In-paper inconsistency — Slack request count exceeds its method count.** §5 states that for the single-method scenario "we prompt the LLM to iterate over each method and generate one request per method" (p. 8), yet Tab. 1 (p. 9) lists Slack with 247 methods and 266 single-method requests. Recorded, not resolved.

## Reading order

Given the notes, read in this order:

1. **§3.3, pp. 5–6** — the ILP. This is the direct structural comparison to the notes' min-cut: same posture (optimize over a graph to get a minimal safe configuration), opposite objective (cover what the plan needs vs. cut what reaches `B`). Read the objective and the single constraint line first.
2. **§4.4 and §7.2, pp. 7–8 and 12–13** — the out-of-scope boundary and the fine-grained-access-control extension, read together. This pair is where MiniScope names the gap that steerability signatures fill, and states why it declined to fill it (permission fatigue).
3. **§3.2, p. 5** — OAuth-derived hierarchy, including the naming-vs-function finding. Relevant to the notes' assumption of "sound skill summaries": MiniScope's answer is to derive structure from a published authorization artifact rather than from a summary.
4. **§6.2.1 and Tab. 3, p. 11** — the six overprivileged connectors. The strongest empirical evidence in the paper, and evidence of a kind the notes do not currently have.
5. **§4.3, p. 7** — the four-option session permission model, if the human-in-the-loop axis is of interest; skip if not.
6. **§6.2 with Fig. 6, p. 10** — worth opening in the PDF rather than the text dump, since Fig. 6 does not survive extraction.
7. **§5 and §5.1, pp. 8–9** — dataset construction, last, unless a test bed is the reason for reading.

Do not attempt pages 15–23 from the extracted text: they are empty after reference removal, and Alg. 1 (referenced on p. 5) is not recoverable from it. Fetch the PDF if the hierarchy-construction algorithm is needed.
