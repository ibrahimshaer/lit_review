## Skip

- **Threat model: indirect prompt injection from untrusted tool/data sources** (§3, p. 4–5). The notes already assume this setting in their title line and in the contamination-event framing (notes line 9).
- **Argument-level manipulation as the residual risk after control-flow protection** (§2, p. 3: "while the *control flow* is protected by the Dual LLM pattern, the *data flow* can still be manipulated", with the SQL-injection analogy). This is the same premise the notes record under Steerability Signatures (notes line 7) — that an adversary's influence lands on skill/tool *parameters*.
- **Natural-language judgement of argument safety is unreliable → use explicit machine-checkable constraints instead** (§5.3, p. 9: capabilities as tags rather than semantic inspection). Covered by notes line 7.
- **Mediation happens at invocation time, before the tool runs** (§5.4 "Enforcing security policies", p. 11). Covered by the notes' inline reference monitor (notes line 3).

## Read

- **§4, PI-SEC security game** (p. 5, Figure 3; CaMeL's instantiation in Figure 4, p. 6). New: a game-based definition where the adversary supplies an initial memory `mem*` and wins if the execution trace contains a tool call outside the allowed set `Ω_prompt`. The notes have no adversary-game formalism — they state the reachability formulation directly (notes lines 4–5).
- **§5.1, Privileged LLM / Quarantined LLM split with code generation** (p. 7). New: the plan is emitted as Python by a P-LLM that never sees tool output, and untrusted parsing is delegated to a Q-LLM restricted to structured output plus a `have_enough_information` boolean. Nothing in the notes separates planning from data handling.
- **§5.2, policies as arbitrary Python functions returning `Allowed`/`Denied`** (p. 8–9, Figure 6). New: policies are executable code, not a graph annotation or a DSL, and are written per-tool.
- **§5.3, the two capability dimensions actually implemented: provenance and allowed readers** (p. 9). New relative to the notes, which name an "initial capability set" (line 4) without saying what a capability contains. Readers are either the `Public` singleton or a set of user identities; provenance is `User`, `CaMeL`, or a tool id, with tools able to declare an *inner* source (e.g. `read_email` tags the sender).
- **§5.4, custom Python interpreter over a restricted dialect, with STRICT and NORMAL dependency modes** (p. 9–10). New: STRICT mode adds the branch test or loop iterable as a dependency of every variable assigned inside the block. This is the paper's mechanism for control-flow-mediated leakage and has no counterpart in the notes.
- **§5.4, error handling with redacted exception messages** (p. 10). New: exceptions are fed back to the P-LLM up to 10 times, and any exception text with a dependency on untrusted data is redacted before the P-LLM sees it. Also states CaMeL has no atomicity or rollback for tool calls that already had side effects (p. 10).
- **§6.1–6.1.3, utility evaluation on AgentDojo** (p. 11–12) and **§6.2, security evaluation** (p. 14–16). New: an empirical evaluation across four suites. The notes record no evaluation at all.
- **§6.1.2, CaMeL-inherent failure modes** (p. 11–12): "data requires action" (the plan depends on data only the Q-LLM can see), underdocumented tool output formats, and the Q-LLM's inability to say *which* information is missing. These are the utility costs of exactly the plan/data separation the notes' architecture also implies.
- **§6.4, data flow becoming control flow** (p. 17–18, Figure 12). New: if the user's own task is "find an action in my email and do it", the generated plan enumerates all tools and selects one from untrusted data, so isolation alone gives the adversary arbitrary action choice; the paper says this attack applies to other security systems too (p. 17).
- **§6.5, token overheads** (p. 18–19). New: cost accounting for the defense.
- **§7, side channels — three concrete ones** (p. 19–21): loop-count leakage to an external fetch (Figure 14, p. 19), one-bit leakage via an adversary-induced exception halting execution before an observable tool call (Figure 15, p. 20), and a timing channel via `time` (Figure 16, p. 21, noted as not exploitable because `time` is absent from the interpreter). The paper attributes the exception channel to the use of exceptions rather than result types (p. 21). Directly relevant to the notes' claim that unsafe paths are *disconnected* — these are paths outside the graph.
- **§8, secondary threat models** (p. 22, Figure 17): a malicious installed "spy tool" whose documentation prompt-injects the agent into routing all data to it, and a rogue/compromised user who is themself the source of the bad argument. The paper says neither is addressed by AgentDojo (p. 22).
- **§9.1, why capability systems historically failed to be adopted** (p. 23): implementation cost, and the requirement that the whole tool ecosystem understand capabilities or utility degrades. CHERI is used as the case study. Bears on the notes' precondition of "sound skill summaries and policies" (notes line 3).
- **§9.2, de-classification and user fatigue** (p. 24). New: blocked actions become user confirmation prompts, and desensitisation is the failure mode.
- **§9.3, the ROP analogy** (p. 24). New: the paper conjectures an attacker can approximate a forbidden control flow by chaining individually-permitted small blocks, as in return-oriented programming against CFI. This is the sharpest available objection to a minimum-cut argument and the notes do not consider it.
- **§10, future work** (p. 24–25): a language with explicit error handling (Haskell) instead of Python; formal verification of the interpreter itself; integrating contextual-integrity tooling (AirGap) and LLM-generated policy DSLs for policy automation.
- **§5, explicit rejection of enumerating `Ω_prompt`** (p. 6) and **§5.3, explicit rejection of coarse control/data-flow rules in favour of per-value tags** (p. 9). New as a stated design argument.

## Disagreements

- **Minimum-cut disconnection of graph paths vs per-value capabilities.** Notes line 5: "Graph-based formulations enable such transitions to be analyzed through reachability and allow unsafe paths to be disconnected using minimum-cut techniques." CaMeL argues against exactly this granularity: "While control and data flows can define coarse-grained invalid execution sequences, they can be restrictive and cause significant utility loss. Capabilities offer a more fine-grained approach by precisely defining, for each individual data, what can be done with that data" (p. 9). CaMeL's stated example is that a policy at the flow level cannot distinguish a phone number from a passport number flowing into the same booking tool (p. 9).
- **Whether cutting paths to the forbidden set suffices.** The notes treat reachability to `B` as the quantity to control (notes line 9). CaMeL states the ROP objection: "an attacker might be able to create a malicious control flow by approximating it with the smaller control flow blocks that are allowed by the security policy" (p. 24), and separately demonstrates a case where the user's own legitimate task makes tool choice a function of untrusted data, so "data flow effectively becomes control flow" (p. 17). Both are transitions the graph would have to already contain to be cut.
- **Whether the graph closes all channels.** Notes line 9: restrictions are recomputed so as to disconnect "all paths to forbidden states on the execution graph." CaMeL: "we find that CaMeL is vulnerable to side-channel attacks ... While side-channels to a degree undermine the claim of strong security guarantees" (p. 19), with the loop-count and exception-halting channels as instances (p. 19–21). These leak without traversing an edge of the graph.
- **Policies as a given vs policies as the open problem.** Notes line 3 conditions the whole result on "sound skill summaries and policies." CaMeL: "CaMeL suffers from users needing to codify and specify security policies and maintain them. CaMeL also comes with a user burden" (p. 24), and "in practice the choice of annotations, their granularity, and levels of access are defined based on a specific use-case" (p. 8–9). Policy derivation is listed as future work, not an assumption (p. 25).
- **Typed parameter constraints vs typed *values*.** Notes line 7: the steerability signature "specifies the type and permitted value range of each parameter." CaMeL attaches metadata to values (readers, provenance) rather than declaring admissible ranges per parameter, and puts the admissibility logic in per-tool Python policy functions instead (p. 8–9). Not a contradiction of fact, but the two papers locate the same constraint in different places.
- **Note on a possible misfiling in the notes:** notes line 3 names "an inline reference monitor" as the mediation mechanism. CaMeL's equivalent — the interpreter checking policies before each tool call (p. 11) — is *not* inline in the model; it is an external interpreter the model cannot see. Worth checking the anchor for which sense "inline" carries.

## Reading order

Given the notes as the target:

1. **§5.3, p. 9** — capabilities as provenance + readers, and the explicit argument for per-value tags over flow-level rules. This is the head-on alternative to the notes' graph-cut design.
2. **§9.3, p. 24 (ROP paragraph)** and **§6.4, p. 17–18** — the two objections a reachability-and-min-cut claim has to answer. Read these before defending the notes' formulation.
3. **§7, p. 19–21** — the three side channels, i.e. what escapes any graph-based confinement. Figure 15's exception channel is the one with a stated fix (result types instead of exceptions, p. 21).
4. **§5.4, p. 9–10** — STRICT vs NORMAL dependency modes; this is CaMeL's answer to control-flow-mediated leakage and the closest thing it has to the notes' recomputation-on-contamination step.
5. **§5.1–5.2, p. 7–9** — the P-LLM/Q-LLM split and policy form, for how the mediation point is actually wired.
6. **§4, p. 5–6** — the PI-SEC game, if the notes' forbidden set `B` needs a security definition to sit inside.
7. **§6.2–6.3, p. 14–17** and **§6.5, p. 18–19** — the numbers to cite against, and the token cost of the approach.
8. **§9.1–9.2, p. 23–24** — adoption cost and user fatigue, i.e. the practical objections to requiring sound per-skill policies.
9. **§6.1.2, p. 11–12** — the utility failure modes, last: useful but the least load-bearing for the notes.
