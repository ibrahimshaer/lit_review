## Skip

- **Threat model (p. 4–5, Sec. 3.2).** Covered by the notes' framing of indirect prompt injection: benign user query, attacker controls any tool return `o_i` for `i > 0`, attacker cannot touch agent internals (p. 5). The notes' premise "SkillGuard ... mediates invocations with an inline reference monitor" assumes the same attacker position.
- **Enforcement point is the tool call (p. 2–3, Sec. 2.2).** The notes already take invocation mediation as given ("mediates invocations with an inline reference monitor"); Progent's argument for why tool calls are the enforcement point (structured name + typed args vs. unstructured reasoning, p. 3) adds rationale, not mechanism.
- **Per-argument constraints instead of NL judgement (p. 5, Sec. 4.1).** Progent's rule form `E t when {e_i}` — boolean conditions over the `i`-th argument, with comparisons, `in`, regex `match`, `length` — is the same move as the notes' steerability signatures ("SkillGuard defines explicit constraints for each skill parameter ... the type and permitted value range"). Covered by the Steerability Signatures note.
- **Default-deny (p. 6, Alg. 2 line 8).** Calls matching no rule are blocked. Implicit in the notes' reference-monitor framing; nothing new.
- **Multimodal out of scope (p. 12, Sec. 9).** Text-only agents; the notes do not raise modality either.

## Read

- **Sec. 4.3, Policy comparison via SMT (p. 6).** New: the expansion/narrowing relation between two policies is reduced to an SMT query `∀ v̄. Φ_{P'_t}(v̄) ⇒ Φ_{P_t}(v̄)` (Eq. 4, p. 6), decided per tool. This is the structural alternative to the notes' reachability/min-cut formulation — a set-inclusion check on allowed calls rather than a graph cut.
- **Sec. 5, Policy update split into two LLM sub-steps (p. 7).** New: the "does an update seem needed?" decision is made *without* the tool result `o_i` in context; only if it says yes does a second call see `o_i` and produce the candidate `P'`. A context-isolation trick the notes have no counterpart for.
- **Sec. 6, Monotonic confinement (p. 7).** New: the stated guarantee is `A(P^(0)) ⊇ A(P^(1)) ⊇ ...` between approved expansions (Eq. 6, p. 7) — the action space may only shrink without explicit approval. The notes' capability restriction is triggered by contamination events; Progent's is unconditional between approvals.
- **Sec. 7, Generic policies and priority layering (p. 7–8).** New: manually written policies that hold across all tasks, composed with the task policy by Algorithm 4 (generic first, task policy only on `f_default`), giving *Generic Confinement* `A(P_generic, P) ⊆ A(P_generic)` (p. 7); multiple stakeholders layer as `(((P_A, P_B), P_C), P_D)(c)` (p. 7).
- **Sec. 7, Approver module (p. 8).** New: expansion handling is a configurable policy of its own — auto-approve all, auto-deny all, per-tool auto-approval for trusted contexts, or human review. The notes have no human-in-the-loop element.
- **Sec. 7, Implementation (p. 7).** New: policies as JSON Schema, enforced with the `jsonschema` library, compared with Z3; library mode (middleware/wrapper) vs. proxy mode (redirect LLM API and MCP endpoints). Sample policy JSON in Figure 9 (p. 14).
- **Sec. 4.1, Fallback actions (p. 5).** New: three fallbacks — terminate, request user inspection, or return an error message. The default returns a per-rule `{reason}` message to the agent so it can retry a different route (p. 5). A recovery channel the notes do not describe.
- **Sec. 8.3, MCP-based benchmark (p. 10–11).** New: AgentDojo's environments, tools, benign tasks, and attack tasks migrated to MCP servers so real frameworks can be attacked in a sandbox; used against LangChain, OpenAI Agents SDK, OpenHands, and an AutoGen multi-agent system with one coordinator and six expert sub-agents (p. 11).
- **Sec. 9, Deployability trade-off (p. 11–12).** New: proxy mode cannot protect built-in tools that bypass external MCP interfaces; library mode can, at the cost of a few lines of code.
- **App. E, Adaptive attacks (p. 14–15).** New: three attacks aimed specifically at the update channel — "If-then-else", "Allow attack tool call", and AgentVigil automated red-teaming.
- **Sec. 10, Related work positioning (p. 12).** New and directly relevant: Conseca and DRIFT also generate agent policies with an LLM but "rely on an LLM for generating the policies without deterministic verification" (p. 12); CaMeL requires modifying agent internals; FIDES requires up-front label assignment; f-secure uses manually assigned trust labels.

## Disagreements

1. **Whether an LLM-derived artifact can be assumed sound.**
   - Notes: "Given sound skill summaries and policies, SkillGuard represents security-relevant transitions with a Skill Impact Graph..." — soundness of summaries and policies is a premise.
   - Progent, p. 7: "the contextual information obtained from the environment at runtime cannot always be considered trustworthy. Consequently, updating the policy based on potentially untrusted context requires careful design to prevent new attack surfaces." And p. 12, aimed at Conseca and DRIFT: they "rely on an LLM for generating the policies without deterministic verification ... even if the LLM-generated policy update is manipulated by adversarial inputs, the expansion check prevents any silent privilege escalation."
   - The gap: Progent treats policy soundness as the thing that must be *checked deterministically at each update*, not assumed. If SkillGuard's summaries/policies are LLM-derived, Progent's argument applies to it directly.

2. **When capability restriction fires.**
   - Notes: "SkillGuard recomputes capability restrictions upon state contamination ... When a contamination event is committed, SkillGuard evaluates the reachability from the current state q to the forbidden set B." — restriction is event-triggered, and requires detecting contamination.
   - Progent, p. 7: "the set of allowed tool calls forms a monotonically decreasing sequence between approved expansions: `A(P^(0)) ⊇ A(P^(1)) ⊇ ...`" — restriction is the default at every step, with no contamination detector in the loop.
   - The gap: SkillGuard's guarantee is conditional on correctly recognising contamination; Progent's is not conditional on recognising anything, but pays for it with approval prompts on legitimate expansions.

3. **Whether expansion is even permitted.**
   - Notes: "disconnecting all paths to forbidden states on the execution graph at a minimal cost" — the objective is a minimum cut, i.e. minimal *utility* loss subject to safety, decided by the system.
   - Progent, p. 4: "Expansions require explicit approval before taking effect. Progent supports configurable approver settings, such as automatically denying all expansions, routing them to a human for review, or automatically approving all."
   - The gap: SkillGuard optimises the restriction automatically; Progent refuses to make that call and escalates it. Progent's own data says the escalation is cheap (6% of updates, p. 4) and that automating it in the permissive direction costs security (Auto-Approve 1.0% vs. Auto-Deny 0.7% ASR, Fig. 5, p. 10).

4. **Same-privilege attacks.**
   - Notes: forbidden state `B` is the safety target; anything not reaching `B` is admitted.
   - Progent, p. 5: "Progent cannot be used to defend against attacks that operate within the least privilege for accomplishing the user task. An example is preference manipulation attacks, where an attacker tricks an agent to favor the attacker product among valid options."
   - Not a contradiction so much as a shared blind spot that the notes do not record. Progent goes further and *removes* two such AgentDojo travel injection tasks from all experiments (p. 14, App. D) on the grounds that they are outside the threat model.

### In-paper inconsistencies (recorded, not resolved)

- **Definition of "expansion" stated two ways.** p. 4 (Sec. 2.2): "We consider an update from `P` to `P'` to be an expansion if the set of tool calls allowed by `P'` is strictly larger than `P`'s." p. 6 (Sec. 4.3): "`P'` is an *expansion* of `P` if `A(P) ⊉ A(P')`." These differ on incomparable policies: a `P'` that both adds and removes calls is an expansion under the p. 6 definition but is not "strictly larger" under p. 4. Algorithm 3 line 7 (p. 6) uses the p. 6 form.
- **"Maintaining utility" vs. the utility bars.** p. 8: "Progent significantly reduces ASR from 39.9% ... to 1.0%, while maintaining utility scores in both no-attack and under-attack scenarios." Figure 3 (p. 9) shows no-attack utility 79.4 → 76.3 and Figure 8 (p. 11) shows larger drops on real frameworks (LangChain 79.4 → 68.0, OpenHands 80.4 → 73.2). Whether a 3–11 point drop counts as "maintaining" is not addressed.
- **Auto-Approve described as improving security.** p. 10: "the Auto-Approve mode allows policies to expand beyond their initial invariants, which improves both utility and security compared to the Disable Update mode. However, the ASR is slightly higher than in the Auto-Deny mode." Both halves are consistent with Figure 5 (2.5 → 1.0 → 0.7), but the paper simultaneously calls Auto-Approve "the worst-case scenario, where all expansions are accepted without review" (p. 9) and uses it as the default for all headline numbers.
- **"About 90% of attacks" (p. 10)** for claude-sonnet-4 (6.8 → 0.5) and Meta-SecAlign-70B (4.8 → 0.3) understates the figure values, which give 92.6% and 93.8%. Left as reported.
- **Section cross-references drift.** p. 4 says generic policies and the approver module are "detailed in Section 7"; Section 7 is titled "Implementation" and does contain them, but the abstract (p. 1) and contributions (p. 2) attribute the policy machinery to Sections 4–6 and the evaluation to "Sections 7 and 8". p. 9 refers to "the benchmarks used in Section 8" from within Section 8.3.

## Reading order

Given the notes, read in this order:

1. **Sec. 4.3, p. 6** — the SMT reduction. This is the direct structural competitor to the Skill Impact Graph + reachability formulation in the notes, and it is two pages shorter than that formulation would be. Read Eq. 1–4 before anything else.
2. **Sec. 6, p. 7** — monotonic confinement. One page; states the guarantee the notes' capability restriction mechanism is trying to reach by a different route.
3. **Sec. 5, p. 7 (Policy Update paragraph)** — the two-sub-step update with `o_i` withheld from the first call. Cheapest transferable idea in the paper.
4. **Sec. 7, p. 7–8** — generic policies, Algorithm 4, priority layering, approver module. This is where Progent's stakeholder model lives, and the notes have nothing corresponding to it.
5. **Sec. 10, p. 12** — the Conseca / DRIFT / CaMeL / FIDES / f-secure / AirgapAgent / IsolateGPT paragraph. The clearest statement in the paper of what counts as a contribution in this space; useful for positioning SkillGuard.
6. **App. E, p. 14–15 with Fig. 10** — adaptive attacks against the update channel. Read this before trusting any policy-update mechanism, including the notes'.
7. **Sec. 8.2, p. 9–10 with Fig. 5** — the approver ablation. Quantifies what automating the expansion decision costs.
8. **Sec. 4.1–4.2, p. 5–6** — skim only; steerability signatures already cover the per-argument-constraint idea.
9. **Sec. 2, p. 2–4** — skip unless the running example is wanted for exposition.
